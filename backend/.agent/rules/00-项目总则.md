# 项目总则

## 1. 项目定位

本项目是**双服务协作架构**：

### Go Auth Service（backend/）

独立部署、独立运行的认证服务。

核心职责：

- 用户注册（auth_users 表）
- 用户登录
- 密码验证
- Access Token 签发（JWT RS256）
- Refresh Token 签发 + Rotation
- Token Revocation / Replay 检测
- JWT Authentication Middleware
- 用户身份管理（/me）
- Request ID 全链路传递
- Rate Limit
- **Go → Python Agent 反向代理**（覆盖 X-User-Id）

### Python Agent Service（agent/）

AI Agent 业务服务，独立部署。

核心职责：

- Chat API（`/chat`, `/chat/stream` —— SSE 流式）
- Agent 推理（LLM + Tool Calling）
- Conversation 管理（conversations 表）
- Message 持久化（messages 表）
- Memory 系统（memories 表 + Qdrant 向量检索）
- RAG
- Kafka 异步消息（Message Consumer + Memory Worker）
- Redis 会话缓存
- Qdrant 向量存储

### 共享基础设施（agent/agent-infra/）

- PostgreSQL 16（双服务共用，各自管理自己的表）
- Redis 7
- Kafka（KRaft 单节点）
- Qdrant
- MinIO（预留）

## 2. 服务边界（不可违反）

```
┌─────────────────────────────────┐
│        Client / Frontend        │
└──────────────┬──────────────────┘
               │
               ▼
┌─────────────────────────────────┐
│      Go Auth Service :8080      │
│  (认证 + 代理 + 安全过滤层)      │
│                                 │
│  /api/v1/auth/*    ← 自己处理    │
│  /api/v1/agent/*   ← 代理转发    │
│                                 │
│  验证 JWT → 覆盖 X-User-Id      │
└──────────────┬──────────────────┘
               │  X-User-Id = user_uuid (UUID)
               ▼
┌─────────────────────────────────┐
│   Python Agent Service :1111    │
│       (Agent 业务 + LLM)        │
└─────────────────────────────────┘
               │
       ┌───────┼───────┐
       ▼       ▼       ▼
    Postgres  Redis   Kafka
                  + Qdrant
```

Go Auth：

> 负责证明"用户是谁"（Authentication）。

Python Agent：

> 负责判断"用户可以访问哪些业务数据"（Authorization）+ 执行 Agent 业务。

**绝对禁止**：

- Go Auth 处理 Agent 业务（直接处理 conversation/message/memory）
- Python Agent 处理登录认证（发 JWT、验密码）
- Go Auth 写 Python Agent 业务表（conversations/messages/memories）
- Python Agent 写 Go Auth 表（auth_users/refresh_tokens）

## 3. 两张用户表的关系

| 维度 | Go Auth 侧 | Python Agent 侧 |
|------|-----------|-----------------|
| 表名 | `auth_users` | `users` |
| 认证字段 | username, email, password_hash | 无（认证由 Go Auth 负责） |
| 跨服务身份 | `auth_user_uuid` (UUID) | `user_uuid` (UUID) |
| 内部关联 | `id` (int64) | `id` (int8) |
| 负责什么 | 登录、密码、JWT | business data 关联 |

**关联规则**：`auth_users.auth_user_uuid = users.user_uuid`

Go Auth 的 [python_user_repo.go](file:///d:/work/agent_system/backend/internal/repository/python_user_repo.go) 在注册时自动 `EnsureUser`，保证 Python 侧 `users` 表有对应的基础记录。

详见 [03-数据库规范.md](file:///d:/work/agent_system/backend/.agent/rules/03-数据库规范.md) 第 2 节。

## 4. 身份链路（不可违反）

```
数据库: auth_users.auth_user_uuid
           ↓
JWT Claims: sub = user_uuid
           ↓
AuthContext (Go): auth_user_uuid
           ↓
Go → Python: X-User-Id = user_uuid
           ↓
Python Agent: 读取 X-User-Id 作为 user_id
```

**数据库内部的自增 id（auth_users.id / users.id）绝对不能作为跨服务用户身份**。

## 5. 核心原则

代码设计优先级：

1. 正确性
2. 安全性
3. 可维护性
4. 可测试性
5. 性能
6. 开发便利性

禁止为了：

- 少写代码
- 追求 benchmark
- 追求所谓高级架构

而牺牲安全性、正确性或可维护性。

## 8. 修改优先级

当任务涉及 Go Auth + Python Agent 两侧时：

### 优先修改 Go Auth

以下场景先改 Go Auth：

- 认证逻辑变更（JWT、密码、Refresh Token）
- 安全策略变更（X-User-Id、Rate Limit）
- Go → Python 代理行为变更
- auth_users / refresh_tokens 表结构变更

### 优先修改 Python Agent

以下场景先改 Python Agent：

- Agent 业务逻辑（chat、memory、tool）
- conversation / messages / memories 表结构变更
- Kafka 消息格式变更
- Qdrant 向量检索逻辑

### 同时修改

以下场景两侧一起改，但要先确认 API Contract：

- 跨服务 Header 变更（X-User-Id、X-Request-Id）
- ChatRequest / ChatResponse 契约变更
- 数据库版本化 SQL 文件（如果涉及跨表）
