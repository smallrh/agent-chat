## 跨会话长期记忆修复（用户问："我是四川人"当前会话记得、新会话就不知道）

### 诊断（架构本来支持跨会话，卡在两个具体缺口）
- 存储/检索 scope **本来就跨会话**：`memories` 按 user_id 存（conversation_id 可 NULL，
  唯一键 UNIQUE(user_id, memory_type, content_hash)）；`retrieval_service.retrieve` 只按
  user_id + is_active 过滤，不含 conversation_id。**所以不是 scope 问题**。
- 缺口 (a) **抽取漏网**：`MemoryTrigger.should_extract` 只在 sequence_id%10==0 或命中信号正则时抽。
  "我是四川人" 不匹配任何正则（原正则只认职业词 / 住在·老家·在…工作），且短会话(<10条)永不触发
  → 事实从源头就没写进 memories。

## 追加修复：profile 改为按 slot 建键（用户反馈"说籍贯会把现居地覆盖掉"）

用户用例：已有 profile `{name, preferences, location:"目前在广州上班", job, school}`，
再说"我的籍贯是四川" → 只会把 `location` 覆盖，而不是新增籍贯 → 回答不准确。

### 根因
`ProfileService` 此前按 **memory_type** 建 profile 键（`_MEMORY_TYPE_TO_PROFILE_KEY`），
而 memory_type 是粗粒度类别：籍贯和现居地**都属于 location**，必然互相覆盖。
（同理多个偏好都属于 preference，也只会保留最后一个。）
而 `memories` 表**本来就有 `slot` 列**且抽取 prompt 已在产出 slot
（residence_city / job_title / favorite_food ...），只是 profile 没用它。

### 改动（3 个文件）
1. `app/service/profile_service.py`（重写）：
   - `_profile_key()`：**优先 slot**，无 slot 才退回 memory_type 兜底键。
   - `build_profile_from_memories()`：先按 updated_at/created_at **升序排序**再覆盖，
     保证"同 slot 最新值胜出"（原来是按遍历顺序碰运气，而 PG 是 importance DESC
     排序，会让最不重要的胜出）。
   - 新增 `PROFILE_SCHEMA_VERSION=2` + `VERSION_KEY="_schema_version"`：
     读到旧/无版本缓存 → 自动从 PG 按新规则重建并回填（**旧 profile 自动迁移**）。
     `update()` 改为走 `get_profile()` 以触发迁移后再合并。
   - `rebuild_from_memories` limit 50→200（slot 细了，条数变多）。
2. `app/kafka/memory_worker.py` prompt：明确 `hometown`(籍贯/老家/祖籍) 与
   `residence_city`(现居/工作地) 是**不同 slot、绝不能合并**；多个偏好也要分开
   （favorite_food / favorite_sport ...）。`_EXTRACTION_PROMPT_VERSION` v1→**v2**。
3. `app/agent/agent.py`：`_format_profile_block` 跳过 `_` 开头的内部字段；
   新增 `_SLOT_LABELS` 给常见 slot 加中文标签（籍贯/老家 vs 现居地/工作地），降低模型混淆。

### 顺带修的触发漏网
"我的籍贯是四川" 中间有"的"，原正则要求"籍贯是"紧跟"我" → 漏匹配。
已补 `的籍贯是|的祖籍是|祖籍|的祖籍|的老家` 等变体（长分支写在短分支前）。

### 验证
`_test_cross_session_memory.py` 扩充到 **33 项断言全部通过 ✅**：新增 籍贯/现居地并存、
偏好按 slot 分开、无 slot 退回 memory_type、同 slot 最新版胜出、旧 schema 自动重建且旧键不残留、
内部字段不注入、slot 中文标签可见。

## 排查：Redis `agent:user:1:memories` 是否没用（结论：**只写不读的死缓存**）

- 写：`MemoryService.save` → `redis_repo.push_memory`（memory_worker.py:509，LPUSH+LTRIM 20 条）
- 失效：`redis_repo.clear_memories`（memory_service.py:193 / 269，软删 / 更新时清）
- 读：**`get_memories` 全仓零调用方**（grep 过整个仓库含根目录脚本）；列表/查询一律走 PG
  （`memory_crud_service`）。→ 非崩溃型 bug，是**半成品缓存 / 纯写入负债**：占 Redis 内存、
  每次保存多两条命令，但没有任何逻辑依赖它。
- 附带发现（重要）：用户贴的该 key 的 value **没有 `slot` 字段**，而当前 `extract()`
  （memory_worker.py:169-176）会强制给 slot 兜底（缺则用 memory_type）并写入 dict，
  且该记录同时含 `extract_model/prompt_version/embedding_model` 等后来才有的字段。
  → 判定为**老数据**（slot 机制加入之前写的）或被手工裁剪。
  影响面：Redis 是死数据不影响；但**要检查 PG `memories.slot` 是否也为旧值**——
  若 slot 缺失，profile 重建会退回按 memory_type 建键，籍贯/现居地又会挤到一起
  （新抽取走 v2 prompt 一定有 slot，故"新说的"没问题）。
  自查 SQL：`SELECT memory_id, memory_type, slot, content, prompt_version FROM memories
  WHERE user_id=1 ORDER BY created_at DESC LIMIT 20;`
- 处置建议（待用户拍板）：删除这套 write-only 缓存（连带 `push_memory` 调用点、
  `get_memories`/`clear_memories` 定义、`memory_service.py` 两处 clear 调用）。
  profile 通道已承担"跨会话已知事实"，PG 是权威存储，留着只写不读的状态是纯负债。

## 推荐方案（用户说"给我推荐"——要的是判断不是选项清单）

### C 中期 → 推荐：PG 租约 + Redis Pub/Sub，不引入 Kafka topic
- 任务分发：`tasks` 加 `owner` + `lease_expires_at`，`SELECT ... FOR UPDATE SKIP LOCKED` 抢租约，心跳续租 60s。
- 进度广播：`TaskEventBus` 换 Redis Pub/Sub（事件瞬时、丢得起，不需要 Kafka 持久化）。
- 不推荐 Kafka 分发的理由：要额外带来 topic/consumer/幂等/offset + "建行但消息没发出"的一致性问题，
  而当前真实需求只有"重启不丢任务"（recover_interrupted 已解决）+"将来多副本"，PG 租约 50 行 SQL 就够。
- 升级触发条件：单进程吞吐跟不上 / 单任务分钟级 / 需跨语言消费。

### D 遗忘 → 推荐：只做检索侧降权，不删不归档
- `score_final = cosine × 0.5^(days_since_access / half_life)`，half_life 按 importance 分级
  （>=0.8→180d，0.5~0.8→60d，<0.5→30d），**必须用现有 memories 数据回测校准**（变化率>20% 说明太激进）。
- 只降权不删除的理由：降权改参数可回退、删除不可逆；配合已有的 score_threshold=0.35，
  降到阈值下的记忆自然不注入，效果等同遗忘但数据完整。
- 归档触发条件：单用户 >5000 条 或 检索 p95 明确因数据量上升。

### D 冲突确认 → 推荐：静默收敛 + 事后可追溯，不做弹窗
- 保持静默保留最新；旧值用 `merged_into`/`is_active=false` 留着；加 `GET /memories/{id}/history`。
- 只在同 slot 30 天内变更 ≥3 次时，回答末尾附带一句轻量确认（不打断）。
- 不做弹窗的理由：记忆是后台异步抽取的，抽取发生在对话之后，根本没有合适的弹窗时机。

### 执行顺序（别跳序）
1 修 4 个🔴 → 2 修 4 个已知 bug（连接池/lifespan/message.start/consumer stop）→ 3 tasks 租约

## 交付 4：并行工具「三连问很慢」的诊断与修复（10-09 晚）

用户输入「广州天气 + 22 的 5000 次方 + 介绍琶洲岛」→ 明显变慢。

### 诊断结论：并行代码没问题，慢在别处
- `_diag_parallel.py` 实测：3 个 200ms 工具，串行 604.9 ms → 并发 201.4 ms，**加速比 3.00x**。
  说明 `asyncio.gather` 分支逻辑正确、guard 没有串行化。
- 之前的「2.11x」是测量噪声（用的毫秒级工具，线程调度盖过收益）。

### 三个真因（含一条我上一轮引入的）
1. **calculator 大整数崩溃 → 触发模型重试风暴**（主要元凶）
   - `22**5000` 有 6713 位；CPython 3.11+ 限制 `int→str` ≤ 4300 位
   - `return f"{value}"` 直接抛 `ValueError`，被 `except Exception` 吞成"计算失败"
   - 模型拿到"计算失败"不知道原因 → 换 code_runner → 子进程同样崩 → 再试…
     每轮一次完整 LLM 往返，最多 10 轮 `MAX_TOOL_ROUNDS`
   - **已修**：转字符串前用 `bit_length` 估算位数（不真正转字符串，规避限制），
     超限返回"结果是一个约 N 位的整数，超出可展示范围"
2. **Exa 联网搜索单次 33.21 秒**（外部 API 固有延迟）
   - 并行省的是"三者叠加"，省不掉"最大值"
   - **已调**：`timeout` 30 → 60（原来必然超时），`retries` 1 → 0（超时后重试只会再吃 60s 且仍失败）
3. **模型若一轮只返 1 个 tool_call，并行分支不触发** → 串行多轮
   - 待验证：看日志里 3 个 tool.start 是否同时出现

## 补充：Exa 官方示例实测（用户贴官方 snippet 后验证）

用户贴了 Exa OpenAI 兼容 Responses API 的官方示例（base_url="https://api.exa.ai"、

### 实测结论
**官方流式写法在本环境（openai SDK 3.17.0）下确实会崩**，两种 schema 都复现：
- 官方空 schema `{"type":"object"}` → 16.04s 后 `JSONDecodeError`
- 项目完整 schema → 15.70s 后 `JSONDecodeError`

### 根因（用裸 httpx 抓原始 SSE 流确认）
Exa 的 SSE 流形如：
```
id: 0
event: response.created
data: {...}
: keep-alive        <<< 元凶
event: response.completed
data: {...}
```
`openai/_streaming.py` 遇到 `: keep-alive` 注释行时，拿到的 data 缓冲为空，
直接 `json.loads("")` 抛错；且异常发生在 async generator 内部，**外层 try/except 接不到**。

### 处置
保持非流式 + 改为 httpx 直连 Exa Responses API（不再依赖 openai SDK 的 responses 流解析），
并手写宽容 SSE 解析（跳过注释行、空 data、不可解析事件）。根因已写入 `app/tool/web_search.py` 顶部文档。
timeout 60 / retries 0（见 ADR-013 相关条目）。

## P0：memories 表缺 slot 列（用户贴日志后定位）

### 现象（用户日志）
```
2026-10-09 18:18:27,367 | ERROR | app.service.profile_service |
ProfileService.rebuild_from_memories FAILED: user_id=1
asyncpg.exceptions.UndefinedColumnError: column "slot" does not exist
```
伴随 `RetrievalService.retrieve: no Qdrant hits`。

### 根因
`slot` 是演进期新增列（`profile_service` 按 slot 建键，ADR-004/005）。
最新 `public.sql` 的 CREATE TABLE **有**该列，但**已有库不会自动补列**；
且六个 `_migrate_*.sql` 手工脚本**没有一个加过它**。

### 影响面（关键，比表面大）
- `MemoryRepository.save()` 的 INSERT 引用 `slot` → **每条记忆都写不进 PG**
- `ProfileService.rebuild_from_memories()` 的 SELECT 引用 `slot` → **每次都崩**，降级返回 `{}`
  → profile 块永远为空 → **跨会话记忆根本不生效**
- 两处都有 try/except 吞异常并降级，只在 DEBUG 留痕，所以线上看着"没报错"

这才是之前「新会话记不住用户」问题的真正答案 —— 之前修了 trigger 与注入逻辑，
但源头（写不进库）一直是坏的，所以任何下游修复都不见效。

### 修复
执行 `migrations/V010__memories_slot.sql`（幂等：ADD COLUMN IF NOT EXISTS + 老数据回填 + 索引）。
全新环境不需要（V001 建表已含 slot）。

### 警示
`public.sql` 顶部是 `DROP TABLE IF EXISTS` + `CREATE TABLE`，对**已有数据的库是毁灭性的**，
只能用于初始化全新库。后续 schema 变更一律走 migrations/ 版本脚本。

### 反思
有 migrator 时，启动会发现 V010 未应用并自动补上，不会静默失效。
这个 bug 本身就是「缺迁移管理」的代价，反过来验证了 ADR-012 的判断。
