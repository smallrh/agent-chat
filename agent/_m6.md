
## P0：memories 表缺 slot 列（用户贴日志后定位）

### 现象（用户日志）
```
2026-10-09 18:18:27,367 | ERROR | app.service.profile_service |
ProfileService.rebuild_from_memories FAILED: user_id=1
asyncpg.exceptions.UndefinedColumnError: column "slot" does not exist
```
伴随 `RetrievalService.retrieve: no Qdrant hits`。

### 根因
`slot` 是演进期新增列（`profile_service` 按 slot 建键，ADR-004/005）。
最新 `public.sql` 的 CREATE TABLE **有**该列，但**已有库不会自动补列**；
且六个 `_migrate_*.sql` 手工脚本**没有一个加过它**。

### 影响面（关键，比表面大）
- `MemoryRepository.save()` 的 INSERT 引用 `slot` → **每条记忆都写不进 PG**
- `ProfileService.rebuild_from_memories()` 的 SELECT 引用 `slot` → **每次都崩**，降级返回 `{}`
  → profile 块永远为空 → **跨会话记忆根本不生效**
- 两处都有 try/except 吞异常并降级，只在 DEBUG 留痕，所以线上看着"没报错"

这才是之前「新会话记不住用户」问题的真正答案 —— 之前修了 trigger 与注入逻辑，
但源头（写不进库）一直是坏的，所以任何下游修复都不见效。

### 修复
执行 `migrations/V010__memories_slot.sql`（幂等：ADD COLUMN IF NOT EXISTS + 老数据回填 + 索引）。
全新环境不需要（V001 建表已含 slot）。

### 警示
`public.sql` 顶部是 `DROP TABLE IF EXISTS` + `CREATE TABLE`，对**已有数据的库是毁灭性的**，
只能用于初始化全新库。后续 schema 变更一律走 migrations/ 版本脚本。

### 反思
有 migrator 时，启动会发现 V010 未应用并自动补上，不会静默失效。
这个 bug 本身就是「缺迁移管理」的代价，反过来验证了 ADR-012 的判断。
