### 2026-10-10 · P0 · 搜索结果强制引用 + 禁止无结果编造

**问题**（《现状和不足.md》Agent 缺点 1）
`web_search` 只返回标题+摘要，模型容易脑补地址/评分，或检索失败后照编；原先**只有提示词软约束**，没有硬校验。

**新增** `agent/app/service/grounding.py`（单一事实来源，全部受 `GROUNDING_*` 开关控制）
| 能力 | 说明 |
|---|---|
| `parse_sources()` | 把 web_search 文本解析成结构化来源 `{title, url, snippet}`，兼容 Exa / Tavily 两种输出格式 |
| `classify_single() / classify()` | 判定检索结果状态：`ok` / `empty`（无条目）/ `failed`（超时·报错·未配置 Key）/ `none`（没搜过） |
| `unknown_urls()` | 正文里出现、但工具原文中没有的 URL = 可疑引用（记 WARN 日志，可选剔除） |
| `append_sources()` | 正文一个来源都没引用时，把检索来源补到答案末尾 |
| `enforce()` | 总入口：成功→校验引用+补来源；失败/空→追加「未核实」降级说明 |
| `reminder_for()` | 检索无果时返回注入给模型的**强约束提醒**（紧跟证据，比 system prompt 有效） |

**改动点**
| 文件 | 改前 | 改后 |
|---|---|---|
| `app/agent/agent.py` | 工具结果直接塞回 messages | 搜索无证据时，紧跟结果补一条 `role=system` 提醒（流式 + 非流式两条链路都加） |
| `app/service/chat_service.py` | 自带 `_maybe_append_sources()`（仅按正则捞 URL，无状态判定） | 删除本地实现，统一改调 `grounding.enforce()` |
| `app/core/config.py` | 无 | 新增 `GROUNDING_ENABLED` / `GROUNDING_INJECT_REMINDER` / `GROUNDING_STRIP_UNKNOWN_URLS`（默认 False，只告警不删）/ `GROUNDING_APPEND_FAILURE_NOTE` |

**顺带修掉的既有 bug**：`enforce()` 会先 `rstrip()` 正文再拼附注，而流式补发增量用
`persist_content[len(final_content):]` 切片——正文尾部有空白时会切错位置，把一小段已有正文
**重复补发**给前端。已改为按 `len(final_content.rstrip())` 切片。

**自检结果**（本地跑通，无需外网）
```
parse_sources(Exa 输出)      → 2 条 {title,url,snippet}，URL 正确剥掉尾部句读
classify(超时文本)            → failed
classify(未检索到)            → empty
classify(正常结果)            → ok
unknown_urls(正文含假 URL)    → ['https://www.fake-url.com/x'] 并打 WARN
enforce(检索失败)             → 追加「⚠️ 本次联网检索未返回可用结果，以上内容未经外部来源核实」
enforce(正文未引用任何来源)   → 追加检索来源块
enforce(没调用过搜索)         → 原样返回，不打扰闲聊
```

**验证方式**：起服务后问一个地点/酒店类问题，观察答案末尾来源块；把 `EXA_API_KEY` 置空再问同一问题，
应看到「未核实」提示而不是编造的具体地址。

### 2026-10-10 · P0 · 历史带回工具记录（刷新后工具卡片不丢）

**问题**（《现状和不足.md》Frontend 缺点 2 / 优先级表 P0）

1. 流式链路落库 `metadata.tools` 时**只记了 `id/name/result/status`，漏了 `arguments`**

2. **非流式 `/chat` 完全不落工具轨迹**（`agent.chat()` 没返回 traces，`metadata=None`）。
3. 被取消的那条工具轨迹会以 `status=running` 落库 → 前端回显后永远转圈「调用中…」。

**改动点**
| 文件 | 改前 | 改后 |
|---|---|---|
| `app/agent/agent.py`（`chat()`） | 返回 `{content, messages}` | 收集 `tool_traces`（含 `arguments`），返回 `{content, messages, tool_traces}` |
| `app/service/chat_service.py`（`stream_chat`） | `tool_traces: list[dict]`，只在 `tool.result` 时 append | 改为 `dict[tool_call_id, dict]`：`tool.start` 就建档记入参，`tool.result` 回填结果，落库时按序导出 |
| `app/service/chat_service.py`（`chat()`） | `metadata=None` | 非流式也落 `metadata={"tools": tool_traces}` |
| 落库前定稿 | 直接存 | `status` 统一规范化为 `done`/`failed`，杜绝「永远调用中」 |

**前端**：`ChatPage.loadConversation()` 与 `api/conversations.ts` 原本就已读 `metadata.tools`
（含 `arguments`），`MessageBubble.ToolCard` 也已渲染参数/结果折叠面板——**前端无需改动**，
补齐后端字段即可生效。

**链路确认**：`conversation_repo.list_messages` 已 `SELECT metadata` 并返回 dict；
Go BFF `proxyJSON` 是 raw JSON 透传，不吞字段。**三侧无需额外改动**。

### 2026-10-10 · P1 · 相似 query 不二次搜索 + 单轮搜索次数上限

**问题**（《现状和不足.md》Agent 缺点 1 / 优先级表 P1）
模型拿到标题和 URL 后仍会「换个近义词再搜一遍」；原去重只认**归一化后完全相同**的 query，
「广州天河酒店」→「广州天河区酒店推荐」这种改写法完全躲过去重。

**改动 1：`app/tool/search_cache.py` 增加相似命中**
| 改前 | 改后 |
|---|---|
| 只有精确命中（`hash(query+top_k)`） | 两级命中：`exact`（原逻辑）+ `similar`（相似度达标） |
| 缓存只存文本 | 缓存额外存归一化 query 与 top_k（用于相似度比较与「能否复用」判断） |

相似度算法刻意做得轻：
- 中文按 **bigram**、英文/数字按词切 token
- 分母取 **较小集合**（`交集 / min(|a|,|b|)`）→ 更具体的 query 能命中更宽泛的 query
- 只复用 `top_k ≥ 本次请求` 的旧结果，避免用 3 条结果顶替要 8 条的请求

**改动 2：单轮联网搜索次数预算**（`app/agent/agent.py` 新增 `_SearchBudget`）
超限时**不真的发请求**，直接把限制提示当工具结果返回给模型：
```
[系统限制] 本轮联网搜索次数已达上限（2 次），本次不再发起搜索。
请基于上面已获得的搜索结果作答；若资料确实不足，直接说明「检索结果不足以确认」，
禁止编造地址、评分、价格等具体事实。
```
流式与非流式两条链路共用同一套预算；非搜索工具不受影响。

**新增配置**（`app/core/config.py`）
| 配置项 | 默认 | 说明 |
|---|---|---|
| `SEARCH_DEDUP_SIMILAR_ENABLED` | `True` | 相似去重总开关 |
| `SEARCH_DEDUP_SIMILARITY` | `0.72` | 相似度阈值（0.72 能吃掉换近义词，又不会让「广州酒店」吃掉「北京酒店」） |
| `SEARCH_MAX_CALLS_PER_TURN` | `2` | 单轮最多搜索几次，`0` = 不限 |

**自检结果**
```
put('广州天河区酒店推荐') → get('广州天河区酒店推荐')  = exact   ✅
                        → get('广州天河酒店')        = similar ✅
                        → get('北京烤鸭店')          = None    ✅（不误命中）
                        → get('广州天河酒店', top_k=8) = None  ✅（条数不够不复用）
                        → get 其它 conversation       = None   ✅（不跨会话串味）
_SearchBudget(2)：第 1、2 次放行，第 3 次返回限制提示，calculator 不受限  ✅
```

### 2026-10-10 · P1 · 对话限流 + SSE 超时对齐（网关层）

**问题**（《现状和不足.md》Backend 缺点 2）
对话接口**无限流无配额**；SSE 超时依赖 `AgentTimeout`，长生成易被切断。
排查后发现三处真实缺陷：

1. `http.Client.Timeout = AgentTimeout`（默认 30s）—— 这个超时覆盖**整个请求 + 读取响应体**，
   SSE 流会在第 30 秒被硬切（表现为「回答到一半断掉」）。config 里其实**已经定义了
   `SSETimeout`（10 分钟）却从未被使用**。
2. `http.Server.WriteTimeout = 30s` —— 从「请求读完」起算，覆盖整个响应写过程，同样会切 SSE。
3. `RateLimitService.CheckChat()` 早就写好了，**但没有任何地方调用它**（限流形同虚设）。

**改动**
| 文件 | 改前 | 改后 |
|---|---|---|
| `internal/client/agent_client.go` | 单个 http.Client，`Timeout=AgentTimeout` | 拆成 `http`（普通，AgentTimeout）+ `sse`（SSE，`Timeout=SSETimeout`、`ResponseHeaderTimeout=AgentTimeout`）；`ProxyToAgent()` 新增 `stream bool` 参数决定用哪个 |
| `internal/router/router.go` | `/agent/*` 无护栏 | 挂载 `ChatGuardMiddleware`；新增 `isStreamingRequest()`（在发代理请求**之前**依据路径/Accept 判定，因为那时还没有 Agent 响应） |
| `internal/middleware/chat_guard.go` | 不存在 | **新增**：只对 `/chat*` 生效——① `CheckChat` 频率限流；② `/chat/stream` 额外抢占并发额度（defer 归还）。非 chat 路径（memories/tasks）直接放行 |
| `internal/service/rate_limit_service.go` | 只有频率限流 | 新增 `AcquireStreamSlot()`：按 user_uuid 在 Redis 计数，超限立刻归还并返回 `ErrStreamLimitReached`；带兜底 TTL 防计数泄漏；Redis 故障一律放行 |
| `internal/config/config.go` | 无 | 新增 `CHAT_STREAM_CONCURRENCY`（默认 2）、`CHAT_STREAM_TTL`（11m）、`HTTP_WRITE_TIMEOUT`（15m） |
| `cmd/server/main.go` | `WriteTimeout: 30s` 硬编码 | 改为 `cfg.ServerWriteTimeout`（默认 15 分钟 ≥ `AGENT_SSE_TIMEOUT` 默认 10 分钟） |
| `internal/errors/errors.go` | 无 | 新增 `ErrStreamLimitReached`（429，`STREAM_LIMIT_REACHED`） |
| `internal/handler/conversation_handler.go` | — | 适配 `ProxyToAgent` 新签名（BFF 传 `false`） |

**为什么频率之外还要并发限流**：`CheckChat` 管「每分钟多少次」，
挡不住「同时开 5 个标签页各问一句」——那会直接把 Agent 的连接池/线程池打满。

**前端无需改动**：`streamChat()` 已处理 `!res.ok`，会读取后端 `message` 字段抛出，
ChatPage 直接展示中文提示（「已有对话正在进行，请等待当前回答结束或停止生成后再试」）。

**验证**：`go build ./...` + `go vet ./...` 均通过。
起服务后连续发起第 3 条流式对话应收到 429 `STREAM_LIMIT_REACHED`；
一条超过 30 秒的长回答不再被切断。

### 2026-10-10 · P2 · 真任务队列（后台 worker）+ 任务面板 UI

**问题**（《现状和不足.md》Agent 缺点 5 / Frontend 可扩充「任务面板」）
任务系统此前是**纯 demo**：`TaskService` 只有一个 `_demo_handler`（5 步 `asyncio.sleep`），
且三个真问题没解决：

1. **API 收了 `kind` 参数但 DB 没有这一列** —— 任务落库后类型就丢了，
   前端只能看到「一个在跑的东西」，重启恢复也不知道该用哪个 handler。
2. **进度只有百分比** —— 没有任何「当前在做什么」的粒度，进度条下面无内容可显示。
3. **取消只能靠 `asyncio.Task.cancel()`** —— 但真实 worker 的耗时在 `web_search`
   的**同步 httpx 调用**里（`to_thread`，线程打不断），用户点取消后任务照样跑完。
4. **无并发上限** —— 连点 10 次建任务会把线程池和搜索预算打满，连正常对话都变慢。

**改动 1：tasks 表加列**（`migrations/V011__tasks_kind_step.sql`，纯增量）
| 新列 | 用途 |
|---|---|
| `kind` varchar(32) DEFAULT 'demo' | 任务类型，与注册的 handler 一一对应 |
| `step` varchar(255) | 当前步骤文案，如「检索资料（2/3）：广州天河酒店」 |
| `steps_done` / `steps_total` | 前端渲染「3/5」，也是 retry 的依据 |

**改动 2：真实 worker**（新增 `app/service/task_worker.py`）
| 部件 | 说明 |
|---|---|
| `TaskCancelToken` | 协作式取消令牌：`raise_if_cancelled()` 检查点 + 可中断的 `sleep()` |
| `TaskCancelled` | 与 `asyncio.CancelledError` 区分的「handler 自己发现取消」信号 |
| `research_handler` | 真实调研 worker：LLM 拆子查询 → 逐个 `web_search`（带会话级缓存）→ 用 `grounding.parse_sources` 抽来源 → LLM 汇总成带参考来源的 Markdown 报告 |
| `demo_handler` | 原内置演示 handler 迁到这里 |
| `register_default_handlers()` | 新增任务类型只改本文件一处 |

`research` 的**三级降级**（任一环节失败都不让整条任务变 failed）：
- 拆子查询失败 → 退化成「直接用 goal 原样搜一次」
- 某个子查询无结果 → 跳过它，其余照常汇总
- 汇总 LLM 失败 → 退化成结构化资料摘要（仍带来源）
- 一条都没搜到 → 明确返回「检索未返回可用结果，**不提供未经核实的结论**」

**改动 3：TaskService 增强**（`app/service/task_service.py`）
| 能力 | 说明 |
|---|---|

**问题**（《现状和不足.md》Agent 可扩充「附件（图/PDF）→ 多模态」/ Frontend 可扩充「多模态输入」）

- 大小（`ATTACHMENT_MAX_BYTES`=10MB）/ MIME 白名单 / 单条消息数量（5）三重校验

### 2026-10-10 · P3 · 评测集（离线快评 + 在线黄金问答）

**问题**（《现状和不足.md》Agent 可扩充「评测集：酒店/天气/计算黄金问答，防回归幻觉」）
P0 的「搜索强制引用 + 禁止编造」、P1 的「相似 query 去重」、P2 的「真 worker / 附件注入」
**全是靠人工跑一遍确认的**。没有评测集意味着：下次改提示词、换模型、调阈值时，
没有任何东西会告诉你回归了。

**为什么分两层**

| 层 | 调模型 | 跑多久 | 什么时候跑 | 证明什么 |
|---|---|---|---|---|
| `offline` | 否 | ~0.4s | 每次改动 / CI | 组件没被改坏（确定性硬断言） |
| `online` | 是 | ~90s | 发版前手动 | 模型现在还老实吗 |

在线层**不可达时整层跳过**（黄色提示，不计入失败）——否则 CI 上没开 LM Studio
就会误报一片红，很快大家就不看评测了。

**新增 `agent/evals/`**
| 文件 | 说明 |
|---|---|
| `runner.py` | 主入口：`--layer offline\|online\|all`、`--case` 过滤、退出码（全过 0 / 有失败 1） |
| `cases_offline.py` | 19 条确定性用例：grounding 解析/判定/enforce/unknown_urls、搜索缓存 exact+similar+不误命中、搜索预算、worker 脏输入容错与取消令牌、附件路径穿越/编码兜底/多模态开关、`_build_messages` 的 content part 形态 |
| `cases_online.py` | 8 条黄金问答：计算 ×2、天气、时间、联网检索、**反编造 ×3**（酒店评分/门牌号/电话） |
| `__init__.py` | 刻意**不导入 runner** |

**反编造为什么是条件断言，不是关键词断言**
不能写「回答里不许出现地址」——检索成功时给地址是**正确行为**。真正的守卫是：

- 检索 `failed`/`empty` → 回答必须出现降级话术（未核实 / 不足以确认 / 无法核实 …）
- 检索 `ok` → 回答里引用的 URL 必须都能在工具原文里找到（`grounding.unknown_urls` 为空）

**踩坑记录**
1. `evals/__init__.py` 里 `from .runner import main` 会让 `python -m evals.runner`
   触发 *"found in sys.modules after import of package"* 并导致行为不可预期 → 删掉导入。
2. 第一版有两条用例红，都是**用例自身**的错，不是产品缺陷：
   - 断言写了 `"未核实"`，但降级话术原文是「未经外部来源核实」，不含这个连续子串；
   - 用了 `search_cache.get()` 判相似命中，但 `get()` 按设计**只返回精确命中**
     （相似命中要看 `get_with_meta()` 的 kind；线上 `web_search` 用的正是后者）。

### 2026-10-10 · P3 · 计费 / 配额（用量埋点 + 套餐 + 拦截 + 用量页）

**问题**（《现状和不足.md》Backend 可扩充「计费/套餐（调用次数、搜索次数）」「管理后台 API」）
对话接口此前**完全没有任何总量约束**：`ChatGuard` 只管瞬时（每分钟多少次 / 同时几条流），
管不住「慢慢用一整天」把额度和外部搜索 API 预算烧光；也没有任何地方能看见用量。

**架构：谁写、谁读、谁拦**

```
Agent（每轮结束后写 Redis 计数）
        ↓  usage:{metric}:{user_id}:{YYYYMMDD}
    ┌───────────────┐
    │     Redis     │  ← 日/月两个窗口，各带 TTL
    └───────────────┘
        ↑  Go 读计数 + 读 user_plans 配额 → 拦截（请求进 Agent 之前）
```

拦截**必须**在 Go 侧：等到 Agent 再判，资源已经消耗完了。
计数**必须**在 Agent 侧：只有它知道这轮到底搜了几次、有没有真的产出。

**计量维度**：`chat`（对话轮次）/ `web_search`（联网检索）/ `task`（后台任务）

**Agent 侧**
| 文件 | 说明 |
|---|---|
| `app/service/usage_service.py` | **新增**：Redis `INCRBY` + TTL（日 2 天 / 月 45 天），三个 metric 常量 |
| `app/service/chat_service.py` | 新增 `_record_usage()`：流式 + 非流式**本轮有真实产出后**埋点；web_search 次数从 tool_traces 统计 |
| `app/service/task_service.py` | `spawn_task` / `retry_task` 各 +1 task |
| `app/main.py` | lifespan STEP 8 启动、shutdown 关闭 |

埋点刻意放在**结束时**而不是开始时：LLM 挂掉或被取消的一轮没有产出，不该计费。
**Redis 故障一律放行**（只记日志）——计费系统挂了不能让用户聊不了天。

**Backend 侧**

**与限流的分工**：`ChatGuard` 管瞬时（防打爆连接池），`Quota` 管总量（计费）。
只有 Quota 挡不住「一分钟打 200 次」；只有 ChatGuard 挡不住「慢慢用一整天」。
